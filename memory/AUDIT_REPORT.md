# AVOPT.STORE — отчёт технического аудита (июнь 2026)

Режим: только анализ. В коде, базе и настройках ничего не менялось. Значения секретов, паролей и персональные данные в отчёт не включены.

## 0. Что именно проверено и чего проверить нельзя

Проверено: исходный код в рабочем окружении (`/app/backend`, `/app/frontend`), рабочая (preview) база MongoDB — только структура, счётчики и индексы.

Как проверено:
- собственный статический разбор (ruff, grep-анализ маршрутов, зависимостей, индексов);
- отдельный аудит безопасности (чтение кода, без атакующих запросов);
- отдельное ревью кода (чтение кода, без запуска тестов);
- полный прогон backend-тестов был выполнен ранее в этой же сессии: 530 прошло, 9 пропущено, 0 упало.

Не выполнено:
- сканер уязвимостей зависимостей (`pip-audit`, `yarn audit`) — не запускался; выводы по зависимостям сделаны только по номерам версий;
- ESLint по всему фронтенду — запуск не дал результата; фронтенд (125 компонентов) проверен выборочно, а не целиком;
- нагрузочное тестирование и профилирование;
- визуальное сравнение со страницами боевого сайта.

Недостающий доступ (нужен для полного аудита):
1. Код, реально работающий на avopt.store (Beget). Я вижу только код этого проекта и не могу подтвердить, что на Beget развёрнута та же версия. Нужен архив или git-хеш боевой версии.
2. Боевая база: индексы, объёмы коллекций, сколько записей содержит пароль в открытом виде, есть ли заказы с расхождением оплаты/остатков.
3. Боевые переменные окружения — только список ключей и значение `CORS_ORIGINS`, без секретов. Особенно важно: заданы ли `CORS_ORIGINS`, `YOOKASSA_*`, `FRONTEND_URL`.
4. Конфигурация веб-сервера Beget: проксирование `/api`, заголовки безопасности, HTTPS, закрыт ли `/docs`, как запускается процесс и сколько воркеров.
5. Логи боевого backend за 2–4 недели.
6. Настройки ЮKassa (адрес уведомлений) и Telegram-бота (адрес webhook).

## 1. Architecture Overview

| Слой | Технологии | Размер |
|---|---|---|
| Frontend | React 19, CRA 5 + craco, Tailwind, shadcn/ui (Radix), axios, react-router 7, framer-motion | ~40,9 тыс. строк, 38 страниц, 125 компонентов, 6 контекстов |
| Backend | Python 3.11, FastAPI 0.110, Starlette 0.37, motor/pymongo, PyJWT, bcrypt | ~17,4 тыс. строк, 37 роутеров, ~470 эндпоинтов |
| База | MongoDB, 56 коллекций, идентификаторы — строковые UUID в поле `id` | вторичных индексов нет ни одного |
| Тесты | 43 файла pytest, ходят по HTTP в работающий API и рабочую базу | фронтенд-тестов нет, CI нет |

Точка входа backend — `server.py`: жизненный цикл, фоновая задача отмены просроченных заказов, стартовые миграции, журнал действий (middleware), выключатель функций сайта (middleware), защита cookie по Origin, CORS. Общие зависимости — `database.py`.

Авторизация: JWT HS256 сроком 7 дней без отзыва. Токен выдаётся и в теле ответа, и в HttpOnly-cookie `access_token` (Secure, SameSite=None). Backend принимает либо заголовок `Authorization: Bearer`, либо cookie. Единая зависимость — `get_current_user`.

Роли: `user`, `manager`, `admin`. Проверка роли — около 190 копий `if user.get("role") != "admin"` прямо в обработчиках; для менеджера — `_manager()` и `_own_client()` в `routes/staff.py`. На фронтенде маршруты в `App.js` не обёрнуты защитой: страницы сами делают редирект, реальная защита — на стороне API.

Модули backend по областям:
- каталог и поиск: `products.py`, `parts_finder.py`, `garage.py`;
- заказы и деньги: `orders.py`, `payments.py`, `crypto_payments.py`, `balance.py`, `credit.py`, `promo_codes.py`, `bonus.py`, `rewards.py`, `returns.py`, `invoices.py`, `documents.py`;
- склад: `warehouse.py`;
- менеджеры: `staff.py`;
- администрирование: `admin.py`, `admin_carts.py`, `action_logs.py`, `settings.py`, `features.py`, `maintenance.py`, `analytics.py`, `attention.py`;
- общение: `chat.py`, `telegram.py`, `notifications.py`, `news.py`, запросы клиентов (`requests.py`, `product_requests.py`, `discount_requests.py`, `cart_discount_requests.py`).

Внешние интеграции: Cloudinary (файлы), Resend (почта), Telegram Bot API (чат поддержки), ЮKassa (карты), блокчейн-проверка платежей (web3) и курс валют, LLM через Emergent-ключ (AI-помощник, описания товаров).

Вывод аудита: в текущем виде код содержит способы получить товар или деньги на балансе без оплаты. Нужно проверить, действуют ли они на боевом сайте.

|---|---|---|---|---|

Усиление защиты (P2–P3):
- нет ограничения попыток на вход, восстановление пароля, гостевой чат и AI-эндпоинты (расход LLM-ключа);
- вход и регистрация не приводят e-mail к нижнему регистру, а восстановление приводит;
- при регистрации нет требований к паролю; токен не отзывается при смене пароля и выходе;
- `CORS_ORIGINS` по умолчанию `*` вместе с `allow_credentials=True`; защита cookie пропускает запросы без заголовка `Origin` и доверяет `X-Forwarded-Host`;
- пользовательский ввод без экранирования попадает в `$regex` публичного поиска (`products.py:369-616`, `warehouse.py:552`, `rewards.py:390`, `action_logs.py:100`); у `GET /products` лимит по умолчанию 1000 без верхней границы;
- загрузка файлов: любой тип до 20 МБ целиком в память (`uploads.py`, `chat.py`); `/chat/send-media` принимает произвольную https-ссылку;
- открыты `/docs` и `/openapi.json`; без токена возвращается 403 вместо 401; часть ошибок отдаёт текст исключения клиенту;
- `memory/test_credentials.md` с рабочими тестовыми паролями отслеживается git;
- неатомарное списание баланса (`orders.py:683-687`) и призовых очков (`bonus.py:505-509`).

Проверено и замечаний нет:
- цены, скидки и итог заказа считаются на сервере, клиентским данным не доверяют;
- заказ по номеру выдаётся только владельцу; выгрузка счетов и документов — только администратору;
- менеджер ограничен своими клиентами; закупочная цена менеджеру не отдаётся;
- через профиль нельзя изменить себе роль, статус, скидку или кредитный лимит;
- на фронтенде нет `dangerouslySetInnerHTML`; токен не хранится в `localStorage`;
- `google_credentials.json` в git не попадал и кодом не используется; файл при этом лежит на диске.

## 4. Performance Audit

Backend:
- Вторичных индексов в MongoDB нет ни в одной из 56 коллекций, в коде нет ни одного `create_index`. Все выборки по `users.id`, `users.email`, `orders.user_id`, `products.id`, `notifications.user_id`, `carts.user_id` — полный перебор коллекции. Уникальность e-mail и артикула держится на проверке «найти, потом вставить».
- Каждый авторизованный запрос делает 2 чтения базы в `get_current_user`; каждый не-GET — ещё одно в журнале действий; каждый запрос к `/api` вызывает `refresh_features()`.
- 59 обращений к базе внутри циклов: `warehouse.py` — 18, `bonus.py` — 8, `returns.py` — 8, `staff.py` — 5.
- 48 загрузок списков по 1000+ документов, 12 без ограничения; параметры постраничной выдачи есть только у 17 эндпоинтов.
- Фоновая задача и стартовые миграции выполняются внутри веб-процесса; при нескольких воркерах задача запустится в каждом.

Frontend:
- Все 38 страниц импортируются сразу, разделения кода нет: клиент каталога скачивает и админку.
- 22 таймера опроса: шапка — каждые 3 с и 30 с, уведомления администратора — 3–4 с, контакты — 5 с, кабинет менеджера — 8 с, заказы администратора — 10 с.
- 90 тегов `<img>`, ни одного с `loading="lazy"`; `React.memo` не используется.
- Утечек таймеров не найдено: число `clearInterval` соответствует числу `setInterval`; перехватчик в `AuthContext` снимается корректно. Проверка выборочная.

Откат для каждого пункта: одно изменение — одна контрольная точка, возврат через Rollback платформы. Для пунктов с изменением данных — резервная копия коллекции до начала.

## 10. Подготовка backend/API к Android-приложениям

1. Авторизация по заголовку `Bearer` уже работает. Не хватает: короткоживущий access-токен и refresh-токен, отзыв токенов при выходе и смене пароля, список активных устройств.
2. Версионирование: ввести префикс `/api/v1`, старые пути оставить как псевдонимы.
3. Единый формат ошибок: код ошибки плюс текст. Сейчас тексты частично на английском, частично на русском; без токена возвращается 403.
4. Постраничная выдача для всех списков: каталог, заказы, уведомления, чаты.
5. Модели ответов для всех эндпоинтов, чтобы из `/openapi.json` генерировать клиент для Kotlin.
6. Вся бизнес-логика цен — только на сервере: отдавать готовые цену, скидку и итог, чтобы приложение не повторяло расчёты из React.
7. Push-уведомления (FCM): коллекция токенов устройств и отправка из `notify.py`. Сейчас обновления получаются опросом каждые 3–30 секунд — для мобильного приложения это расход батареи и трафика.
8. Идемпотентность создания заказа и платежа (ключ идемпотентности) — мобильная сеть повторяет запросы.
9. Ограничение частоты запросов по пользователю и устройству.
10. Параметры в теле запроса вместо строки запроса у POST-эндпоинтов (например, `chat/send-media`); загрузка файлов частями.
11. Эндпоинт минимально поддерживаемой версии приложения.
12. Деньги — в копейках целым числом или строкой; даты — единый ISO 8601 в UTC.

Пункты 2–4 и 12 меняют контракт API, поэтому вводятся только в новой версии `/api/v1`, без изменения текущих путей, которыми пользуется сайт.
